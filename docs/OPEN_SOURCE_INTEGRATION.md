# Open-source integration matrix — CDR-01 immersive campus

## Implemented and tested

The campus control room now has a self-hosted Three.js r147 runtime (`dashboard/vendor/three.min.js`), a 3D campus constructed from the same `Campus()` building/stop geometry, a camera with orbit/follow/top views, 2D fallback, an outdoor/logistics visual scene toggle, and nine distinguishable robot silhouette profiles. The robot and trace receive the deterministic replay frames from `cdr_sim/campus.py`. This is **not physics-based 3D navigation**. New local endpoints include `/scene3d.js`, `/vendor/three.min.js`, and `/api/references`; these are read-only.

The vendor source and license are included so the 3D viewer requires **no CDN** to render. The original license from each other referenced repo accompanies exactly one read-only SDF or Xacro sample under `integrations/upstream_samples/`. They are intentionally *not automatically launched*, since dependencies, version requirements, meshes, sensor types and physical assumptions are not interoperable. They are real sourced excerpts, not validated executable simulations.

If you copy an asset or code from the upstream repository later, check that asset's individual license and dependencies.

## How to run the new viewer

From the repository root, with Python 3.11+:

```sh
python scripts/serve_dashboard.py
```

Open http://127.0.0.1:8765. The default is **3D WORLD**, which is genuinely rendered in WebGL. Drag to orbit, scroll to zoom, use **Follow**, **Top**, or **Orbit**, change **Visual robot**, and switch **Campus** / **Logistics**. You can change destination and fault scenario; the actual simulated path still comes exclusively from the Python replay. **2D MAP** remains available for comparison.

To run checks:

```sh
python -m unittest discover -s tests -v
```

The optional GitHub Actions `Campus control-room browser visual checks` workflow opens Chromium at desktop/tablet/phone sizes, checks 3D canvas and model selection, verifies 2D and fault-scenario results, and preserves screenshot artifacts.

## Simulation-data integrity

- **3D**: qualitative visualization generated by WebGL; wheel profile switching changes only the model silhouette. It never changes route physics, speed limits, wheel traction, robot mass or battery.
- **2D replay**: scripted kinematics and waypoint planning; numerical outputs like speed, estimated Wh, SOC and distance are model-derived.
- **Gazebo evidence panel**: historical odometry from a separate physical-simulator headless workflow, not the motion currently drawn in the 3D browser.
- **Not yet performed**: simultaneous verified Gazebo 3D robot/ROS bridge/Nav2 autonomy, LiDAR raycast perception, independent ground-truth versus odometry, contact/actuator validation, real hardware or accredited safety demonstration.

The next engineering milestone is to choose **one** drive base (CDR-01, not nine), import compatible legal meshes with inertias/collision geometries, implement ROS2 sensor topics, and send `/tf`/odometry or timestamped independent ground-truth to the 3D view with clearly separated provenance. This requires actual Gazebo+Nav2 integration and end-to-end tests; do not present existing scripted mission replay as this milestone.
